[BUG 2.1] [RESOLVED & FIXED] Customer Reconciliation Engine Running Balance Calculation
----------------------------------------------------------------------------------------------------
- Status: RESOLVED & VERIFIED WITH AUTOMATED UNIT TESTS (September 30, 2026)
- Kaha Par Hai (File): Backend/src/services/reconciliation.service.js (Lines 156-175)
- Kya Galti Ho Rahi Hai:
  Customer reconciliation service me ledger entries ko traverse karke calculated running balance
  nikalne ka logic likha gaya hai:
  ```javascript
  for (const entry of ledgerDoc.entries) {
    if (entry.entryType === "SALE_CREDIT" || (entry.debit && entry.debit > 0)) {
      running += Number(entry.unpaidAmount || entry.debit || 0);
    } else if (entry.entryType === "PAYMENT_RECEIVED" || (entry.credit && entry.credit > 0)) {
      running -= Number(entry.paymentAmount || entry.credit || 0);
    }
  }
  ```
  Lekin `customer.model.js` (Lines 175-186) aur `customerLedger.repository.js` me schema fields ka naam:
  -> `entry.creditAmount` (Udhaar amount)
  -> `entry.debitAmount`  (Payment amount)
  hai!
  `entry.unpaidAmount`, `entry.paymentAmount`, `entry.debit`, aur `entry.credit` naam ke fields
  CustomerLedger schema me EXIST HI NAHI KARTE!
  
- Asar (Impact):
  `Number(entry.unpaidAmount || entry.debit || 0)` humesha `0` ban jata hai!
  Iska matlab `authoritativeBalance` hamesha `0` calculate hota hai!
  Agar merchant ya admin Reconciliation page par ja kar "Auto-Fix" dabayega, to code execute karega:
  `Customer.updateOne({ _id: customer._id }, { $set: { currentBalance: 0 } })`
  Yaani ki dukandar ke saare customers ka lakhon rupaye ka Udhaar ek click me DATABASE SE PERMANENTLY ZERO ho jayega!
  
- Sahi Solution:
  Field names ko schema ke mutabiq match karna:
  ```javascript
  for (const entry of ledgerDoc.entries) {
    if (entry.entryType === "SALE_CREDIT") {
      running += Number(entry.creditAmount || 0);
    } else if (entry.entryType === "PAYMENT_RECEIVED") {
      running -= Number(entry.debitAmount || 0);
    } else if (entry.entryType === "ADJUSTMENT") {
      running += Number(entry.creditAmount || 0) - Number(entry.debitAmount || 0);
    }
  }
  ```

[BUG 2.2] CONCURRENCY KILLER: Atomic Decrement ke baad `.save()` call karke Stock Corrupt Karna
----------------------------------------------------------------------------------------------------
- Kaha Par Hai (File): 
  1. Backend/src/repositories/sale.repository.js (Line 306)
  2. Backend/src/repositories/inventory.repository.js (Lines 324 & 599)
- Kya Galti Ho Rahi Hai:
  Code me inventory ko concurrency-safe banane ke liye `Inventory.findOneAndUpdate` use kiya gaya:
  ```javascript
  const updatedInv = await Inventory.findOneAndUpdate(
    { _id: update.inventory._id, businessId, availableStock: { $gte: update.quantity } },
    { $inc: { availableStock: -Math.abs(update.quantity) } },
    { new: true, ...sessionOpt }
  );
  // Iske turant baad ye line likh di gayi:
  updatedInv.lowStockAlert = updatedInv.availableStock <= (updatedInv.reorderLevel || 5);
  await updatedInv.save(sessionOpt); // <-- YE SABSE BADI GALTI HAI!
  ```
- Asar (Impact):
  Jab aap Mongoose me `findOneAndUpdate` karte hain aur fir usi document instance par `.save()` call
  karte hain, to Mongoose us document ki purani in-memory state ko database par rewrite kar deta hai.
  Example Dekhiye:
  1. Product ka stock hai 10.
  2. Cashier 1 ne 2 item beche -> DB me ho gaya 8. Cashier 1 ke computer ki memory me `updatedInv` = 8 hai.
  3. Usi second Cashier 2 ne 3 item beche -> DB me atomic update hua aur DB me stock ho gaya 5.
  4. Ab Cashier 1 ka thread line 306 par `await updatedInv.save()` run karta hai. Memory me 8 tha, to wo DB me wapis 8 likh deta hai!
  5. Cashier 2 ka 3 item ka deduction Gayab ho gaya! DB me 5 ki jagah wapis 8 dikhane laga!
  
- Sahi Solution (STATUS: RESOLVED & VERIFIED ✅):
  `findOneAndUpdate` ke baad kabhi bhi `.save()` call mat karo. Agar `lowStockAlert` update karna hai
  to usko atomic query me `$set` karo ya isolated `Inventory.updateOne` se update karo:
  ```javascript
  const isLow = updatedInv.availableStock <= (updatedInv.reorderLevel || 5);
  await Inventory.updateOne(
    { _id: updatedInv._id },
    { $set: { lowStockAlert: isLow, updatedAt: new Date() } },
    sessionOpt
  );
  ```
  - Backend Resolution: sale.repository.js (L304) and inventory.repository.js (L322 & L597) updated to use isolated Inventory.updateOne.
  - Frontend Resolution: POSTerminalPage.jsx and InventoryAuditPage.jsx updated to immediately trigger real-time catalog re-fetch upon INSUFFICIENT_STOCK or concurrency rejection.
  - Verification: Automated test Backend/tests/test-bug-2.2-concurrency-save-fix.js passed 100% (3/3).

[BUG 2.3] Sequential Number Generator Race Conditions (Invoice, PO, GRN)
----------------------------------------------------------------------------------------------------
- Kaha Par Hai (File):
  1. `Backend/src/repositories/sale.repository.js` (`getNextInvoiceNumber`, Lines 18-30)
  2. `Backend/src/repositories/purchaseOrder.repository.js` (`generateNextPoNumber`, Lines 16-39)
  3. `Backend/src/repositories/grn.repository.js` (`generateNextGrnNumber`, Lines 14-35)
- Kya Galti Ho Rahi Hai:
  Teeno repositories me naya number generate karne ke liye:
  `Invoice.countDocuments({ businessId })` ya `PurchaseOrder.findOne().sort({ createdAt: -1 })`
  call kiya jata hai aur loop me `exists` check hota hai.
- Asar (Impact):
  Agar do cashiers ek hi second me checkout karte hain:
  Donon ko same count milta hai (e.g., dono ne count dekha 100, dono ne banaya INV-1101).
  Jab dono insert karne jate hain, to MongoDB ka unique index:
  `{ businessId: 1, invoiceNumber: 1 }` second cashier ka checkout FAIL kar deta hai:
  `MongoServerError: E11000 duplicate key error collection: invoices`.
  POS screen par error popup aa jata hai aur customer ka bill ruk jata hai.
- Sahi Solution (STATUS: RESOLVED & VERIFIED ✅):
  Ek dedicated `counters` collection banao jo atomic `$inc: { seq: 1 }` se next number de:
  ```javascript
  const counter = await Counter.findOneAndUpdate(
    { businessId, sequenceName: "INVOICE" },
    { $inc: { seq: 1 } },
    { returnDocument: "after", ...sessionOpt }
  );
  return `INV-${counter.seq}`;
  ```
  - Backend Resolution:
    1. Created `Backend/src/models/counter.model.js` with compound unique index `{ businessId: 1, sequenceName: 1 }`.
    2. Created `Backend/src/repositories/counter.repository.js` with atomic `$inc` sequence generator, cold-start max-sequence detection from existing documents, and duplicate key race recovery.
    3. Updated `sale.repository.js` (`getNextInvoiceNumber`), `purchaseOrder.repository.js` (`generateNextPoNumber`), and `grn.repository.js` (`generateNextGrnNumber`) to use `counterRepo.getNextSequence()`.
  - Frontend Resolution: POS Checkout, PO Creation, and GRN modal endpoints automatically receive strictly collision-free, monotonic identifiers with zero 11000 duplicate key rejections.
  - Verification: Automated test `Backend/tests/test-bug-2.3-sequential-counter-race-fix.js` passed 100% (5/5 concurrent & cold-start tests).

[SECURITY 3.1] CRITICAL: Insecure Dynamic CORS with Credentials (Arbitrary Origin Reflection)
----------------------------------------------------------------------------------------------------
- Kaha Par Hai (File): `Backend/src/app.js` (Lines 26-46)
- Loop Hole Code:
  ```javascript
  app.use(
    cors({
      origin: (origin, callback) => {
        return callback(null, true); // Har incoming domain ko blindly ALLOW kar raha hai!
      },
      credentials: true, // Aur browser cookies/auth headers bhi allow kar raha hai!
      ...
    })
  );
  ```
- Kyu Khatarnak Hai (Vulnerability Breakdown):
  Ye OWASP Top 10 A01 (Broken Access Control) ki critical vulnerability hai.
  Agar VendorOS ka koi user kisi malicious website (e.g. `evil-site.com`) par click karta hai, to
  `evil-site.com` background me user ke logged-in session ke sath VendorOS ki APIs ko call kar sakti hai.
  Browser cookies ke sath request bhejega aur backend use "OK" kar dega.
  Attacker user ke saare invoices, customer phone numbers, aur business balance chura sakta hai.
- Sahi Solution:
  Har origin ko allow mat karo. Sirf authorized frontend domains ki whitelist banayein:
  ```javascript
  const allowedOrigins = (process.env.ALLOWED_ORIGINS || "http://localhost:5173").split(",");
  app.use(cors({
    origin: (origin, cb) => {
      if (!origin || allowedOrigins.includes(origin)) return cb(null, true);
      cb(new Error("CORS policy violation"), false);
    },
    credentials: true,
  }));
  ```

[SECURITY 3.3] HIGH: JWT Tokens Stored in LocalStorage (XSS Session Hijacking)
----------------------------------------------------------------------------------------------------
- Kaha Par Hai (File):
  `Frontend/src/services/api.js` (Lines 17-25, 76-84)
- Loop Hole Code:
  Backend accessToken aur refreshToken dono cookies me bhi bhejta hai aur JSON body me bhi bhejta hai.
  Frontend interceptor unhe utha kar `localStorage` me save kar deta hai:
  ```javascript
  localStorage.setItem("accessToken", accessToken);
  localStorage.setItem("refreshToken", newRefreshToken);
  ```
- Kyu Khatarnak Hai:
  `localStorage` ko website par chalne wali koi bhi JavaScript read kar sakti hai.
  Agar frontend me koyi bhi third-party npm package me XSS flaw aaya ya injected script run hui,
  to attacker `localStorage.getItem("refreshToken")` se token chura kar permanent login bana lega.
- Sahi Solution (STATUS: RESOLVED & VERIFIED ✅):
  1. Frontend Hardening (`api.js`):
     - `localStorage.setItem("accessToken")` aur `localStorage.setItem("refreshToken")` ko completely remove kiya gaya.
     - In-memory token management (`inMemoryAccessToken`) implement kiya gaya jo sirf JavaScript runtime heap me rehta hai aur persistent browser storage me kabhi write nahi hota.
     - On initialization, `localStorage.removeItem("accessToken")` and `localStorage.removeItem("refreshToken")` actively purge any legacy tokens.
     - 401 response interceptor silently calls `/api/auth/refresh` with `{ withCredentials: true }`. Browser automatically sends the `HttpOnly` refresh token cookie and updates `accessToken` & `refreshToken` HttpOnly cookies without exposing them to JavaScript.
  2. Frontend Context Hardening (`AuthContext.jsx`):
     - `user` state initialization and authentication status no longer rely on `localStorage.getItem("accessToken")`.
     - Authentication state is verified through secure `/api/auth/me` HttpOnly cookie handshake.
     - `login()` and `logout()` purge tokens from localStorage and reset in-memory state.
  3. Authentication Flow Hardening:
     - `Login.jsx` and `VerifyOTP.jsx` updated to eliminate token storage in `localStorage`.
  4. Verification:
     - Frontend production build `npm run build` executed successfully without errors (2,442 modules transformed).
     - Unit test `Backend/tests/test-security-3.3-cookie-auth.js` passed 100% (Pure HttpOnly cookie authentication verified with zero headers and zero localStorage access).

  - `Backend/src/models/customer.model.js` (Lines 226-235)
  - `Backend/src/models/supplier.model.js` (Lines 256-290)
- Galat Design:
  Customer aur Supplier dono ke ledger transactions ko ek hi document ke andar array bana kar store
  kiya gaya hai:
  ```javascript
  const customerLedgerSchema = new mongoose.Schema({
    businessId: { type: ObjectId },
    customerId: { type: ObjectId },
    balance: Number,
    entries: [customerLedgerEntrySchema], // <-- Unbounded Array!
  });
  ```
- Kyu Galat Hai:
  MongoDB me ek single document ka maximum size **16MB** hota hai.
  Ek dukan me regular customer ya supplier ke saal me hazaron transactions hote hain.
  1. Jaise-jaise entries badhengi, har baar naya transaction hone par MongoDB ko pura multi-megabyte document memory me uthana padega aur wapis likhna padega.
  2. Ek limit ke baad document 16MB se bada ho jayega aur `BSONObjectTooLarge` error fek dega. Us customer ka Udhaar account permanent freeze/corrupt ho jayega.
  3. `customerLedger.repository.js` me line 373 par `allEntries.slice(skip, skip + limit)` kiya gaya hai. Yaani 10,000 entries pehle Node.js memory me aayengi, fir slice hongi!
- Sahi Design:
  Jaise aapne `InventoryLedger` ko ek standalone collection banaya hai, waise hi:
  `CustomerLedgerEntry` aur `SupplierLedgerEntry` ko bhi alag independent collection banana chahiye
  jisme `{ businessId, customerId, createdAt }` par index ho aur native `.skip().limit()` chale.
