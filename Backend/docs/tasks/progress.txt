[✓] C26. T33: Customer Ledger Transaction Log & Sub-Ledger History
    - Purpose & Core Rule: "T33 establishes the complete financial history for each customer, recording every credit sale (Udhaar) and repayment settlement (Jama) in an append-only, immutable transaction ledger. It maintains real-time running balances using the authoritative formula: Balance = Previous Balance + Credit - Debit, strictly scoped to businessId."
    - Ledger Schema & Conventions:
      * `creditAmount`: Udhaar taken by customer (increases outstanding balance).
      * `debitAmount`: Payment/settlement made by customer (decreases outstanding balance).
      * `balance`: Authoritative running balance snapshot at transaction completion.
      * `saleId` / `invoiceId`: Direct relational link to historical invoice and line items for complete invoice traceability.
      * `entryType`: Enum (`SALE_CREDIT`, `PAYMENT_SETTLEMENT`, `OPENING_BALANCE`, `ADJUSTMENT`).
    - Append-Only Immutability Rule:
      * Customer ledger records are never modified or deleted (`no PUT/DELETE`).
      * Discrepancies or opening balance migrations are handled via adjustment transactions (`POST /api/customers/:id/ledger`).
    - Endpoints Implemented:

      * `POST /api/customers/:id/ledger`: Append manual opening balance or adjustment transaction to customer ledger.
      * `POST /api/customers/:id/settle`: Settle customer Udhaar with repayment debit and automatic ledger record creation.

- [RESOLVED] BUG 2.2: Concurrency Killer: Atomic Decrement followed by .save() Stock Corruption:
  * Files:
    - `Backend/src/repositories/sale.repository.js`
    - `Backend/src/repositories/inventory.repository.js`
    - `Frontend/src/features/pos/POSTerminalPage.jsx`
    - `Frontend/src/features/inventory/InventoryAuditPage.jsx`
  * Issue: Calling Mongoose `.save()` on an in-memory document instance after atomic `findOneAndUpdate` overwrote concurrent stock decrements made by other checkout terminals with stale values.
  * Fix:
    - Backend: Replaced `.save()` with targeted `Inventory.updateOne({ _id }, { $set: { lowStockAlert, updatedAt } })`, preserving exact concurrent atomic stock changes.
    - Frontend: Added instant catalog re-fetch (`fetchPOSProducts()`) upon `INSUFFICIENT_STOCK` rejection and inventory table sync on conflict error.

- [RESOLVED] BUG 2.3: Sequential Number Generator Race Conditions (Invoice, PO, GRN):
  * Files:
    - `Backend/src/models/counter.model.js` (Created dedicated atomic counter schema)
    - `Backend/src/models/index.js` (Exported Counter model)
    - `Backend/src/repositories/counter.repository.js` (Created centralized atomic sequence generator)
    - `Backend/src/repositories/sale.repository.js` (Integrated atomic getNextInvoiceNumber)
    - `Backend/src/repositories/purchaseOrder.repository.js` (Integrated atomic generateNextPoNumber)
    - `Backend/src/repositories/grn.repository.js` (Integrated atomic generateNextGrnNumber)
    - `Backend/src/services/grn.service.js` (Passed session context to generateNextGrnNumber)
  * Issue: Previous generator calculated next sequential numbers via countDocuments/findOne + in-memory loop check, causing simultaneous POS checkouts or PO/GRN creations to generate identical IDs and crash with MongoServerError E11000 duplicate key error.
  * Fix: Implemented atomic MongoDB `$inc` counter collection with automatic cold-start seeding from existing documents, backward compatibility, and race condition duplicate key recovery.
  * Test: `Backend/tests/test-bug-2.3-sequential-counter-race-fix.js` -> 100% Passed.
